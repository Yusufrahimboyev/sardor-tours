# Uzbek / English / Russian Localisation Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Serve the whole Sardor Tours site in Uzbek (Latin), English and Russian under `/uz/`, `/en/`, `/ru/`, with equal status for all three.

**Architecture:** All routes move under a `[lang]` segment whose layout is the root layout (`<html lang>`). A redirect-only middleware adds the prefix to unprefixed URLs. UI text lives in typed JSON dictionaries. Tour data is split into a language-neutral base plus one text file per language. A tiny in-house `t()` (no i18n library) serves server components directly and client components through a provider that holds only the `client` namespace.

**Tech Stack:** Next.js 15.5 (App Router, Turbopack), React 19, TypeScript, zod 3, react-hook-form, Playwright (system Chrome), Node 22 `node:test` via `tsx` (new dev dependency, unit tests only).

**Spec:** `docs/superpowers/specs/2026-11-10-i18n-uz-en-ru-design.md`

## Global Constraints

- Locales are exactly `uz`, `en`, `ru`. No i18n library dependency.
- Intl locale tags: `uz` → `uz-Latn-UZ`, `en` → `en-GB`, `ru` → `ru-RU`. OG locales: `uz_UZ`, `en_GB`, `ru_RU`.
- Uzbek uses **Latin** script.
- Locale resolution order: `lang` cookie → `Accept-Language` (`uz*` → uz, `ru*` → ru) → `en`.
- Middleware redirects are **307** and preserve the query string. Never touch `/api`, `/_next`, or paths with a file extension.
- Cookie: `lang=<code>; Path=/; Max-Age=31536000; SameSite=Lax`.
- Every existing `/en/...` URL keeps resolving. Legacy `/booking/ST-XXXXXX/` redirects to `/{lang}/booking/ST-XXXXXX/`.
- Slugs stay English in all languages. Prices stay GBP and come only from base tour data.
- `Booking.tourName` is stored in **English**. `Booking.lang` / `ContactMessage.lang` are new. Records missing `lang` are treated as `en`.
- WhatsApp prefilled texts are in the customer's language and always include the booking reference and the English tour name in brackets.
- `alternates.languages` = `{ uz, en, ru, 'x-default': '/en/…' }`. `robots` disallows `/api/` and `/*/booking/`.
- Every plural object in every language includes `other`. RU uses `one/few/many/other`, UZ and EN use `one/other`.
- Proper names, prices, times and slugs are never altered by translation.
- `tomorrowISO()` keeps its Cairo time-zone behaviour (uncommitted fix in `src/lib/dates.ts` — commit it in Task 2).

## Review Focus

1. **Real-world `Accept-Language` headers** (`ru-RU,ru;q=0.9,en;q=0.8`, `uz-Cyrl-UZ`, `de-DE,ru;q=0.5`, `*`, empty). Expected: the highest-weighted *supported* language wins, else `en`. Pinned in Task 1 (`resolveLocale` tests).
2. **A stale or tampered `lang` cookie** (`lang=de`, `lang=`). Expected: ignored, falls through to `Accept-Language`. Pinned in Task 1.
3. **Non-page URLs hitting the middleware** (`/api/tours`, `/sitemap.xml`, `/robots.txt`, `/icon.svg`, `/manifest.webmanifest`). Expected: served directly, no redirect. Pinned in Task 4 (`i18n.spec.ts`).
4. **API clients that send no `lang` or an unknown one** (old cached JS, `lang: "de"`). Expected: treated as `en`, never a 400 for that reason alone. The schema uses `z.enum(LOCALES).catch('en')` (a deliberate hardening of the spec's `.default('en')`). Pinned in Task 7.
5. **Unknown tour slug under a non-English locale** (`/ru/sharm/no-such-tour/`). Expected: HTTP 404 with the Russian not-found page. Pinned in Task 6.
